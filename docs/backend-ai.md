# Внешний backend генерации целей

```
приложение → https://game-of-aim-backend.onrender.com/api/goals/generate
```

Генерация целей вынесена во внешний HTTP-сервис: клиент отправляет `POST` с JSON `{ "user_id": "...", "goal_text": "..." }` и ожидает `200`. Код сервиса в этот репозиторий не входит.

Адрес задаётся в `env.json` (`BACKEND_API_URL`) или при сборке:

```bash
flutter run --dart-define=BACKEND_API_URL=https://example.com/api/goals/generate
```

Если сервис не нужен, оставьте значение по умолчанию или пустую строку: ручной конструктор цели и библиотека пресетов работают без него.

## Почему сервис «спит»

Бесплатный тариф Render останавливает контейнер после ~15 минут простоя. Первый запрос после этого ждёт загрузки, и игрок думает, что приложение зависло.

**Что делает клиент** (`lib/services/backend_warmer.dart`):

- при запуске игры и дальше раз в 10 минут отправляет лёгкий `GET` в корень сервиса — контейнер поднимается, пока игрок ходит по экранам;
- диалог создания цели греет сервис, пока игрок набирает текст;
- перед запросом генерации ждёт пробуждения (`ensureAwake`) и только потом отправляет запрос, поэтому игрок ждёт один раз, а не дважды;
- если ответа нет дольше 4 секунд, вместо молчаливого спиннера показывает «Сервис ИИ просыпается после простоя».

Само засыпание клиент вылечить не может: пока приложение свёрнуто, система останавливает таймеры, а когда приложение закрыто — прогрев не идёт вообще. **Полное решение — регулярный внешний пинг** каждые 10–14 минут.

## Вариант 1 (рекомендуется): внешний мониторинг

UptimeRobot или cron-job.org с проверкой раз в 5–10 минут. Бесплатно, не тратит минуты CI и работает независимо от того, играет кто-то или нет.

Что проверено на живом сервисе (замеры из этого проекта):

| Запрос | Ответ | Время (сервис разбужен) |
|---|---|---|
| `GET https://game-of-aim-backend.onrender.com/` | `200 OK` | 0.33 с |
| `GET https://game-of-aim-backend.onrender.com/health` | `404` | 0.27 с |

Отдельного `/health` в backend **нет**, и добавлять его не обязательно: корень уже отдаёт `200` и отвечает быстро. Поэтому в мониторинг ставится корневой адрес:

- **URL:** `https://game-of-aim-backend.onrender.com/`
- **Интервал:** 5 минут (гарантированно меньше 15-минутного окна Render и есть запас на пропущенную проверку)
- **Ожидаемый код:** `200`
- **Таймаут:** не меньше 60 секунд. Если поставить 30, проверка может оборваться на пробуждении, и сервис будет помечен как упавший, хотя он просто поднимался.

UptimeRobot на бесплатном тарифе даёт интервал 5 минут, cron-job.org — от 1 минуты. Лишний смысл в интервале меньше 5 минут появляется только если сервис засыпает быстрее обычного.

**Проверено на живом сервисе.** Монитор UptimeRobot с интервалом 5 минут: после 17 минут полного простоя приложения запрос к корню вернул `200` за 0.773 с (из них 0.517 с — установка соединения), повторный — за 0.221 с. Подъём остановленного контейнера занял бы десятки секунд, поэтому такой ответ означает, что сервис не засыпал: мониторинг удерживает его разбуженным. Сам монитор при этом показывал `Up` и 139 мс на проверку.

Сколько именно длится холодный старт, так и осталось неизмеренным — и уже не важно: пока монитор работает, засыпания не происходит. Если число всё же понадобится, поставьте монитор на паузу на 20 минут и выполните:

```bash
curl -o /dev/null -s -w '%{time_total}\n' https://game-of-aim-backend.onrender.com/
```

## Вариант 2: Scheduled Pipeline в GitLab CI

Если backend живёт в GitLab, расписание — это обычный pipeline (CI/CD → Schedules, cron `*/10 * * * *`), и он **расходует минуты CI**.

Бесплатный тариф GitLab.com даёт **400 минут в месяц** на пространство имён, а расход = `длительность задания / 60 × коэффициент` (для обычного Linux-раннера коэффициент 1). Расписание раз в 10 минут — это 4320 запусков в месяц:

| Длительность задания | Минут в месяц | Влезает в 400? |
|---|---|---|
| 3 секунды | ~216 | да |
| 5 секунд | ~360 | впритык |
| 10 секунд | ~720 | нет |

То есть вариант рабочий только если job укладывается в считанные секунды (`curl` без установки зависимостей, только `rules` для расписания):

```yaml
keep-awake:
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
  script:
    - curl -sS -m 60 -o /dev/null -w '%{http_code}\n' "$BACKEND_URL/"
```

## Другие варианты

- **Платный инстанс Render** — засыпания нет вовсе.
- **Сократить холодный старт** (правки в backend): меньше образ (например, `python:3.12-slim` вместо полного), ленивая загрузка тяжёлых моделей вместо импорта на старте, `--workers 1` у uvicorn, отказ от локальных ML-библиотек в пользу внешнего API.

Часы бесплатного тарифа Render: 750 часов в месяц на рабочее пространство. Один сервис, работающий круглосуточно, — это ~730 часов, то есть в лимит укладывается, но второго бесплатного сервиса рядом уже не поместить: он будет засыпать или не запустится.
