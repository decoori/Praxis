# База данных

Серверная часть PRAXIS — проект Supabase: PostgreSQL, Auth и RLS-политики. Приложение не создаёт схему само: миграции применяются вручную и по порядку.

## Как применить

1. Создайте проект Supabase.
2. Откройте **SQL Editor**.
3. Выполните файлы из `migrations/` по номерам: `001` → `022`. Каждый файл — отдельный запуск: при ошибке SQL Editor прерывает пакет и не откатывает уже выполненное.
4. Возьмите из **Project Settings → API** адрес проекта и publishable (anon) ключ, положите их в `env.json` (шаблон — `env.example.json`).

Первые миграции идемпотентны по объектам (`if not exists`, `drop policy if exists`), но при наличии грязных данных упадут на этапе ограничений — это намеренно. Сначала применяйте на тестовом проекте.

| `007_shop_and_camp_rpc.sql` | `buy_consumable` и `upgrade_camp`: покупки и постройки считает сервер, цена берётся из таблицы, `auth.uid()` только внутри функции |
| `008_fix_uuid_text_comparison.sql` | исправление сравнения `uuid = text`: в 006 проверка владельца квеста ломала сдачу квестов (ошибка 42883). Приводит id игрока к uuid во всех серверных функциях |
| `009_complete_quest_text_compare.sql` | сдача квеста переведена на сравнение по `text`: каст на параметре (008) ошибку 42883 не убрал, поэтому все идентификаторы в функции приводятся к одному типу единообразно |
| `010_fix_last_active_date_type.sql` | истинная причина поломки сдачи квестов: `last_active_date` — `date`, а в него присваивался `text`. `v_today` стал `date`, сравнение однотипное |
| `011_fix_reward_multipliers.sql` | награда за квест снова считается с множителями серии и бонусов лагеря (в 010 начислялся голый номинал) |
| `012_evolve_and_streak_rpc.sql` | `evolve_era` и `restore_streak`: пороги эпох в таблице `era_config`, проверка XP и лагеря 5/5 на сервере, списание 150 золота за спасение серии |

## Особенность: uuid против text

В этой базе идентификаторы игрока в `friendships.user_id`, `preset_votes.user_id` и `goal_presets.author_id` хранятся как **text**, а `auth.uid()` возвращает **uuid**. Неявного приведения между ними в PostgreSQL нет, поэтому в политиках этих таблиц стоит явный каст `auth.uid()::text`.

Сравнение `uuid = text` без каста — ошибка 42883, которой один раз уже была сломана сдача квестов. Актуальные определения функций проверяет `test/sql_safety_test.dart`; промежуточные версии в старых миграциях намеренно не проверяются — это история.

## Лиги и сезоны

Система рейтинга устроена как в Duolingo, но без повышений и понижений:

- **Лига** определяется накопленным опытом `profiles.total_xp` (Бронзовая с 0, Серебряная с 1000, Золотая с 2500, Платиновая с 5000, Изумрудная с 10000, Алмазная с 20000). Пороги лежат в `league_tiers` — менять их можно без правки клиента.
- **Соревнование** идёт по опыту, набранному за текущий сезон (`season_xp`). Сезон длится 7 дней, открытый сезон существует всегда.
- **Награда** — золото за топ-3 каждой лиги (300 / 200 / 100, таблица `league_rewards`). Итоги подводит первый зашедший игрок: `pg_cron` не нужен, функцию `settle_league_season` вызывают загрузка игры и обновление вкладки «Рейтинг». Повторный вызов безопасен: сезон помечается `settled_at`, а начисление защищено уникальностью `(season_id, user_id)`.
- **Зачёт** — место в таблице и награда достаются одним и тем же игрокам: только тем, у кого есть опыт за сезон. Остальные участники лиги видны в списке с прочерком вместо места.

Почему появился `total_xp`: рейтинг раньше сортировался по `profiles.xp`, но этот счётчик **тратится на эволюцию** (`xp = xp − порог эпохи`), поэтому развивающийся игрок падал в рейтинге ниже того, кто копит опыт и не эволюционирует. `total_xp` не уменьшается никогда.

Ограничение бэкфилла: при вводе `total_xp` прошлый опыт восстановить было нечем — он нигде не хранился отдельно от потраченного. Всем проставлен текущий `xp`, поэтому у игроков, которые уже эволюционировали, история начинается с текущего значения.

## Промокоды

Создать код можно из SQL Editor:

```sql
insert into public.promo_codes (label, description, gold, xp, energy, shields, max_redemptions, expires_at)
values ('praxis2026', 'Стартовый набор', 500, 100, 3, 1, 100, now() + interval '30 days');
```

`label` — то, что вводит игрок: латиница, цифры, `_`, `-`, 3–32 символа, регистр не важен. `max_redemptions = null` — без общего лимита.

## Очистка тестовых данных

`scripts/reset_all_player_data.sql` удаляет все учётные записи (`auth.users`), цели, квесты, дружбы, голоса, сессии фокуса, использования промокодов, награды и сезоны лиг. Остаются промокоды, системные пресеты (`sys_%`), конфигурация лиг и эпох, схема и функции.

Это **не миграция**: файл лежит вне `migrations/` намеренно. Не применяйте его на базе с живыми игроками.

Запускать блоками, а не одним куском: при ошибке SQL Editor прерывает пакет и не откатывает уже выполненное. Первый и последний блоки считают строки во всех таблицах схемы — по ним видно, что было и что осталось.

## Модель доступа

- Экономика (награды, магазин, постройки, эволюция, серия, слоты, рейтинг пресетов) считается SQL-функциями. Прямые `update` с клиента остались только для смены ника, выбора аватара и правки названия своего квеста.
- Каждая функция, принимающая id игрока параметром, обязана сверить его с `auth.uid()`. Правило зафиксировано тестом `test/sql_safety_test.dart`.
- `profiles` читается по политике `select using(true)` — это нужно таблице лидеров. Ники, эпоха и опыт публичны; считать таблицу приватной нельзя.
